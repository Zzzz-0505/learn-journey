## 1. 用户能做什么？

至少这些：

1. 创建知识条目：填写标题、正文、标签、来源等。
2. 查看知识条目：按 id 查单条，或分页列表。
3. 搜索知识：关键词、标签、状态、作者、时间范围过滤。
4. 修改知识条目：更新标题、正文、标签、状态。
5. 删除或归档知识：软删除、归档、恢复。
6. 管理批注：给知识条目新增、修改、删除、查询批注。
7. 管理标签：给知识打标签、按标签筛选。
8. 导入导出：批量导入知识，导出知识库。
9. 登录与权限管理：如果做多用户，需要认证和授权。
10. 查看版本历史或审计日志：谁在什么时候改了什么。

P2 核心先做 1 到 6，7 到 10 可以后置。

## 2. 系统需要哪些模块？

至少 4 个，我会分成 6 个核心模块，外加 1 个可选增强模块：

1. API 接入模块
2. 鉴权模块
3. 知识服务模块
4. 存储模块
5. 检索模块
6. 模型与校验模块
7. AI 增强模块，可选

## 3. 每个模块负责什么？

- API 接入模块：接收 HTTP 请求，解析参数，调用服务层，返回统一响应。
- 鉴权模块：识别当前用户，判断能不能读、写、删、批注。
- 知识服务模块：编排知识条目和批注的业务规则。
- 存储模块：负责数据库读写、事务、分页查询。
- 检索模块：负责关键词、标签、状态、排序和分页检索。
- 模型与校验模块：定义请求、响应、数据库模型和字段规则。
- AI 增强模块：可选，做 embedding、自然语言入口、语义相似度，不进入核心 CRUD 主流程。

## 4. 模块之间怎么交互？

上传一条知识，数据流我会这样画：

客户端 `POST /knowledge`
→ API 接入模块：认证、解析 JSON、校验请求体
→ 知识服务模块：业务校验、去重、格式化、决定创建
→ 存储模块：开启事务，写入知识表
→ 数据库：返回新 id
→ 可选：写审计日志、发索引事件
→ API 接入模块：返回 `201` 和知识条目 JSON

查询一条知识：

客户端 `GET /knowledge/{id}`
→ API 接入模块：认证、参数校验
→ 知识服务模块：权限检查
→ 存储模块：按 id 读取
→ 返回知识条目或 `404`

新增批注：

客户端 `POST /knowledge/{id}/comments`
→ API 接入模块：认证、校验
→ 知识服务模块：确认知识存在、检查权限
→ 存储模块：写入批注表
→ 返回批注 JSON

如果以后要做自然语言入口，它应该是单独入口，比如 `/assistant`。先由意图模块解析，再转换成内部服务调用。核心 CRUD 不由 LLM 猜操作，因为 HTTP 方法和路径已经表达得很清楚。

## 5. 数据结构长什么样？

一条知识条目至少这些字段：

| 字段 | 说明 |
|---|---|
| id | 唯一标识 |
| title | 标题，必填 |
| content | 正文，必填 |
| content_type | text、markdown、json 等 |
| summary | 摘要，可选 |
| tags | 标签数组 |
| source | 来源 |
| author_id | 作者或创建者 |
| status | draft、published、archived、deleted |
| version | 版本号，用于并发控制 |
| created_at | 创建时间 |
| updated_at | 更新时间 |
| deleted_at | 软删除时间 |
| metadata | 扩展字段 |

一条批注至少这些字段：

| 字段 | 说明 |
|---|---|
| id | 批注唯一标识 |
| knowledge_id | 关联的知识条目 id |
| author_id | 批注作者 |
| content | 批注内容 |
| anchor | 可选，定位到原文位置 |
| status | active、deleted |
| created_at | 创建时间 |
| updated_at | 更新时间 |

## 6. 可能出什么错？

至少这些：

1. 未认证或 Token 无效。
2. 权限不足，不能修改别人的知识。
3. 请求体不是合法 JSON。
4. 必填字段缺失，比如标题或正文为空。
5. 字段类型错误，比如 tags 不是数组。
6. 内容超长，超过数据库或业务限制。
7. 资源不存在，查不到指定 id。
8. 重复创建，同一来源或标题冲突。
9. 并发更新冲突，版本号不一致。
10. 分页参数非法，比如 page 为负数。
11. 数据库连接失败或事务失败。
12. 存储配额超限。
13. 检索服务不可用。
14. 批注锚点失效，定位不到原文。
15. 如果启用 AI，LLM 或 embedding 超时。

## 7. 文件结构怎么组织？

我会按层组织，不按 add、delete、change 这种动作拆文件。目录树可以是这样：

```text
knowledge_api/
  app/
    main.py                 # 创建应用，注册路由、中间件和异常处理
    core/
      config.py             # 读取环境变量和运行配置
      security.py           # 认证、授权、Token 相关逻辑
      errors.py             # 统一异常类型和错误响应
      logging.py            # 日志配置
    api/
      deps.py               # 路由依赖，比如当前用户、数据库会话
      routes/
        knowledge.py        # 知识条目 CRUD、列表和搜索接口
        comments.py         # 批注增删改查接口
        health.py           # 健康检查接口
    schemas/
      knowledge.py          # 知识条目请求和响应模型
      comment.py            # 批注请求和响应模型
      common.py             # 分页、错误、通用响应模型
    services/
      knowledge_service.py  # 知识条目业务规则和流程编排
      comment_service.py    # 批注业务规则和权限校验
      search_service.py     # 搜索、过滤、排序、分页编排
    repositories/
      knowledge_repo.py     # 知识条目数据库读写
      comment_repo.py       # 批注数据库读写
    db/
      session.py            # 数据库连接和会话管理
      base.py               # 数据库模型基类
      models.py             # ORM 模型定义
    search/
      keyword_search.py     # 关键词和标签检索实现
      indexer.py            # 可选，把知识写入全文或向量索引
    ai/
      embedding.py          # 可选，文本向量化
      intent.py             # 可选，自然语言入口的意图识别
    tests/
      conftest.py           # 测试夹具和测试数据库初始化
      test_knowledge_api.py # 知识条目接口测试
      test_comments_api.py  # 批注接口测试
      test_services.py      # 服务层单元测试
      test_errors.py        # 异常和边界测试
```

## 8. 怎么验证它是对的？

我会分层次测：

1. 单元测试：测服务层、校验规则、权限判断。
2. 接口测试：用测试客户端调 API，检查状态码和 JSON 字段。
3. 集成测试：接测试数据库，验证真实读写和事务。
4. 异常测试：空输入、非法 JSON、不存在 id、权限不足、并发冲突、分页越界。
5. 契约测试：确认请求和响应结构稳定，错误码统一。
6. 并发测试：两个请求同时更新同一条知识，检查版本冲突。
7. 检索测试：关键词、标签、状态、分页、排序是否正确。
8. 端到端测试：创建 → 查询 → 更新 → 批注 → 删除 → 确认不可见。
9. 回归测试：每次改动跑全套测试。
10. 如果启用 AI：语义相似度只能作为辅助验证，不能替代确定性断言。核心正确性还是靠数据库回读和接口断言。

总结一句：核心顺序应是 API 契约、数据模型、存储、服务、批注、基础检索、测试，最后才是 LLM、embedding 和 RAG。
