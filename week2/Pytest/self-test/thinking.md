## 二、写代码前，你必须先拍板的 2 个坑

这两个坑现在不定，写 schemas 时一定卡住，测试也会写错。

### 坑 1：`PUT /todos/{id}` 时，"title 唯一"跟"我自己"怎么算？

场景：id=1 的待办 title 叫 "买菜"。用户 `PUT /todos/1` 把 title 改成 **"买菜"**（没改）。这算 409 重复吗？

- **算** → 用户只要不动 title 就改不了别的字段，反人类。
- **不算** → 逻辑是："title 唯一" 要排除**自己这条**。即：查有没有**别的** id 用了这个 title，有才 409。

**必须选"不算"**（排除自己）。这是你写 repository 的 `update` 时要专门处理的一行逻辑，也是测试要专门加的一条用例：`PUT` 一条待办，title 保持不变 → 期望 200 而不是 409。**这种"边界用例"就是新手和老手的区别。**

### 坑 2：`deadline` 格式"YYYY-MM-DD"谁来校验？

- 如果 schema 里写 `deadline: date`（pydantic 的 date 类型）→ 传 `"2024-13-40"` 自动 422，你一行校验代码都不用写。
- 如果写 `deadline: str` → 你得自己正则，还得自己抛 422。

**选 `date` 类型**。`schemas.py` 里一行 `deadline: date` 就搞定，FastAPI 返回时也会自动序列化成 `"2024-05-01"`。这就是"用对类型省一半代码"。

### 顺带确认一下 level 的写法

你说"只能传 1、2、3 整数"。两种写法，结果不同：

- `level: int = Field(ge=1, le=3)` → 传 `1.5` 会**先被转成 int 1**（pydantic 的宽松转换），可能悄悄通过。
- `level: Literal[1, 2, 3]` → 传 `1.5`、`"1"`、`2.0` 全 422，**严格**。

你想要"其他都报错"→ **用 `Literal[1,2,3]`**。这条也要在测试里体现（`test_level_float_rejected`）。

# C2 先回答你：limit 监测的是什么"错误"

你问得对，limit 不是"检测错误"，它是**一个用户可调的参数，而用户可能把它调错**。这是两个概念，我拆开说。

`GET /todos?limit=10` 意思是"**最多返回 10 条**"。为什么需要它？因为列表可能很长，用户要分页。那"用户调错"有哪几种：

| 用户传入 | 应该怎样 | 为什么 |
|---|---|---|
| `limit=10` | 200，返回 ≤10 条 | 正常 |
| `limit=-1` | **422 非法参数** | 负数条数没意义 |
| `limit=0` | 200 空 或 422 | 看你怎么定（0 条 = 合法但没意义，建议 422 要求 ≥1） |
| `limit=abc` | **422 非法参数** | 不是整数 |
| `limit=1.5` | **422 非法参数** | 条数不能是小数 |
| 不传 `?limit` | 200，用默认值（如 10） | 默认值兜底 |

**所以 limit 检测的是"非法参数"这一类异常里的一个具体实例**——就像 level 检测"非法参数（越界）"、id 检测"非法参数（类型错）"一样。**它们仨是同一个异常类别（422）的三个不同触发点**，这不叫重复，叫"同一类异常的多个入口"。

**结论**：limit 值得要。它让你的"非法参数"异常有 3 个测试点（id 非整数、level 越界、limit 非法），比只有 1 个更扎实。而且代码上就一行：`limit: int = Query(10, ge=1, le=100)`。
